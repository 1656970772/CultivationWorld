# 世界观通用抽取插件设计

> 最后更新：2026-06-19
> 状态：设计草案，待用户审阅
> 类型：Codex 插件与多 agent 抽取流水线设计

## 背景

用户希望把 `docs/世界观参考/模板/` 下的调研模板沉淀为一个通用 Codex 插件。插件输入为小说原文和模板目录，输出为按模板生成的世界观参考 Markdown 文档。

已确认约束：

1. 插件面向多部小说，不为《凡人修仙传》写一次性流程。
2. 每次执行时长不限制，质量和速度优先。
3. StoryGraph 目前还不稳定，第一阶段不依赖 StoryGraph。
4. 采用“通用插件内核 + 模板流程配置 + 流程型 skills”的方案。
5. 多模板批量执行时必须支持动态调用多 agent，主 agent 负责调度、合并和审计，子 agent 负责独立抽取、复核和质量检查。
6. `出门游历流程分析模板.md` 和 `时间行动与事件耗时模板.md` 已删除，README 中残留条目属于导航文档未同步的问题，后续通过模板一致性检查发现并报告。

当前观察：

- 模板目录包含约 38 个世界观参考模板，模板形态可分为实体清单、事件链、关系变化、世界空间、制度流程、职业机制、叙事场景等。
- 《凡人修仙传》原文约 15.2MB，GBK 编码，约 2451 章。插件必须先处理编码、分章、行号和证据锚点，否则会影响抽取质量。
- 当前工作区已有大量未提交的世界观参考文档和模板改动。插件设计应避免依赖这些未提交内容的具体状态。

## 目标

1. 提供一个多小说通用的 Codex 插件，能根据作品配置、模板配置和流程类型执行世界观抽取。
2. 在不依赖 StoryGraph 的情况下，完成编码识别、分章索引、候选召回、结构化抽取、合并去重、证据回填、覆盖率审计和 Markdown 写出。
3. 对不同模板类型调用不同流程型 skill，而不是用一个万能 prompt 处理所有模板。
4. 使用配置承载作品、模板、字段、触发词、审计规则、输出规则，不在代码中硬编码小说实体、章节或模板细节。
5. 支持长时间运行、断点续跑、失败局部重试和章节级并发。
6. 支持动态多 agent 调度：按作品、模板、流程类型、章节分片和审计阶段分派子 agent，提高速度并降低遗漏风险。
7. 每个最终文档都附带可审计的中间结果和 audit 报告，明确列出低置信候选、缺证据候选、字段缺失、未扫描章节和总表/卡片不一致问题。

## 非目标

1. 第一阶段不实现 StoryGraph 作为主索引库。
2. 第一阶段不要求一次性跑通所有模板，但架构必须能扩展到所有模板。
3. 不把模型输出当作不可审计的最终结论。模型只在局部证据和候选范围内做结构化归纳。
4. 不自动覆盖用户手工修改过的现有文档。默认写草稿或要求显式覆盖。
5. 不生成模板之外的额外正文、插件说明或项目映射内容。

## 总体方案

采用“通用插件内核 + 模板流程配置 + 流程型 skills + 多 agent 动态调度”。

流水线：

```text
小说原文
  -> 编码识别/转码
  -> 分卷分章/行号索引
  -> 全文切片与候选召回
  -> 模板识别与流程路由
  -> 多 agent 分片抽取
  -> 中间结果库
  -> 去重/合并/补证据
  -> 多 agent 审计与复核
  -> 按模板生成 Markdown
```

核心原则：全量不靠模型记忆，而靠候选池、章节覆盖、模板覆盖、证据闭环和审计报告保证。模型负责在可验证片段内做判断，插件负责保证每章都扫过、每类候选都进入池、每个模板都有查漏结果。

## 插件模块边界

建议插件名：`worldview-extractor`。

建议目录：

```text
worldview-extractor/

  bin/
    codex-worldview
  configs/

    templates.yaml
    extraction-rules.yaml
    writer-rules.yaml
  skills/

    event-chain-extractor/
      SKILL.md
    relationship-extractor/
      SKILL.md
    world-space-extractor/
      SKILL.md
    system-process-extractor/
      SKILL.md
    profession-mechanism-extractor/
      SKILL.md
    narrative-scene-extractor/
      SKILL.md
  src/
    source/
    index/
    router/
    executor/
    agents/
    audit/

```

### Source 层

职责：

- 读取多小说、大文本、多编码原文。
- 自动识别编码，优先处理 UTF-8、GBK、GB18030、Big5、Shift-JIS 等常见文本。
- 内部统一转为 UTF-8。
- 保留原始路径、卷章、行号、字符偏移和切片范围。
- 分章失败时降级为固定字数切片，并在 audit 中标红。

### Index 层

第一阶段使用轻量本地索引，不依赖 StoryGraph。

职责：

- 章节索引。
- 行号到字符偏移映射。
- 关键词倒排。
- 实体候选索引。
- 事件候选索引。
- 共现窗口索引。
- 源文件、模板文件、配置文件的变更缓存。

推荐存储：

```text
.worldview-extractor/
  <作品名>/
    source-index.jsonl
    inverted-index.sqlite
    candidates/
    merged/
    audit/
    runs/
```

### Template Router 层

职责：

- 扫描模板目录。
- 读取 `templates.yaml`。
- 检查 README、配置和实际模板文件是否一致。
- 根据模板配置路由到流程型 skill。
- 为每个模板生成执行计划，包括章节范围、候选规则、字段要求、输出规则和审计规则。

发现 README 中仍列出已删除模板时，router 不应静默跳过，而应报告：

```text
模板导航存在但模板文件缺失：
- 出门游历流程分析模板.md
- 时间行动与事件耗时模板.md
```

### Skill Executor 层

职责：

- 根据 route 调用对应流程型 skill。
- 将章节切片、候选片段、模板字段、输出约束交给子 agent。
- 要求子 agent 输出结构化候选卡片，而不是直接写最终 Markdown。
- 收集子 agent 状态：`DONE`、`DONE_WITH_CONCERNS`、`NEEDS_CONTEXT`、`BLOCKED`。
- 对失败分片做局部重试或升级模型。

### Audit + Writer 层

职责：

- 统一去重、合并、证据补齐、字段完整性检查。
- 生成每个模板的 audit 报告。
- 按模板分派 writer agent，并行渲染最终 Markdown。
- 每个 writer agent 只负责一个模板输出文件。
- 每个 writer agent 写完后，必须触发该文档的最终质量审查。
- 文档审查未通过时，主控 agent 将审查报告和原输出重新交给 writer agent 返工，直到通过或进入人工复核。
- 同一个输出文件必须使用独占锁，避免多个子 agent 同时写同一个文件。

## 流程型 skills

不为 38 个模板各写一套独立流程，而是按抽取范式划分为 7 个流程型 skill。

| 流程型 skill | 适合模板 | 核心抽取方式 |
|---|---|---|
| `entity-catalog-extractor` 实体清单抽取 | 丹药、法宝、武器、材料、妖兽、功法术法神通、灵根体质血脉 | 全文召回名称候选，按实体聚合证据，再补字段 |
| `event-chain-extractor` 事件链抽取 | 事件因果链、冲突事件、动态事件与机会点、世界状态与灾变、战斗与保命机制 | 按章节扫描事件，抽起因、过程、结果、后续影响 |
| `relationship-extractor` 关系与角色变化抽取 | 人物关系、NPC 性格、记忆情绪执念、角色修炼历程、角色 AI 行为 | 以人物为锚点，聚合互动、关系变化、行为模式 |
| `world-space-extractor` 世界空间抽取 | 世界观设定、势力设定、秘境遗迹、建筑设施与场所功能 | 抽地点、势力、区域规则、设施功能、空间关系 |
| `system-process-extractor` 制度流程抽取 | 宗门任务体系、散修生存方式、拍卖坊市与交易、物资产出与消耗、信息传播与情报 | 抽触发、参与者、资源、流程、规则、结果 |
| `profession-mechanism-extractor` 职业机制抽取 | 炼丹师、炼器师、阵法师、符师 | 抽职业输入、工具、流程、产出、失败、收益方式 |
| `narrative-scene-extractor` 叙事场景抽取 | 有限视角与叙事日志、相遇剧情与对话设计 | 抽场景、视角限制、对话目的、信息差、情绪变化 |

每个 skill 只输出候选卡片。最终 Markdown 由 writer agent 基于已合并、已审查的数据按模板生成。

## 多 agent 动态调度设计

本插件应吸收 `superpowers:subagent-driven-development` 的执行原则：主 agent 不继承所有任务细节，不让单个上下文承载全部 38 个模板；每个子 agent 获得精确任务、精确输入、精确输出格式；抽取后进入综合质量审查。

### 角色划分

| 角色 | 职责 | 是否写最终文件 |
|---|---|---|
| 主控 agent | 解析请求、读取配置、规划 run、分派子 agent、处理状态、合并结果、决定重试 | 否，只调度 writer agent |
| 索引 agent | 处理编码、分章、行号、倒排索引和缓存 | 否 |
| 模板规划 agent | 对模板进行分类，生成该模板的执行计划和候选规则补充 | 否 |
| 候选召回 agent | 按 route、模板触发词、章节索引和共现窗口召回原始候选 | 否 |
| 分片抽取 agent | 按模板、章节分片或候选集抽取结构化卡片 | 否 |
| 字段补全 agent | 针对候选卡片缺失字段回查上下文，补齐必填字段或写明缺失原因 | 否 |
| 别名归并 agent | 对同模板候选做去重、同名合并、别名合并和冲突保留 | 否 |
| 链路聚合 agent | 对事件链、关系链、流程链等跨章节候选做主题聚合和阶段串联 | 否 |
| 证据定位 agent | 回查原文证据，确认行号、章节、事实摘要和待核验状态 | 否 |
| 覆盖查漏 agent | 按章节、境界、地域、身份、势力、场景和模板字段检查中间数据遗漏 | 否 |
| 质量审查 agent | 检查中间数据和最终文档的模板字段、写全规则、禁止事项、遗漏风险、重复、证据不足、字段空洞和过度推断 | 否 |
| writer agent | 根据单个模板的合并结果、审查结果和输出规则生成一个 Markdown 文档 | 是，只写自己负责的模板文件 |

### 子 agent 输入契约

每个子 agent 必须获得完整但有限的上下文，不依赖主会话历史。

分片抽取 agent 输入：

```yaml
work: 凡人修仙传
template_id: 丹药分析
route: entity-catalog-extractor
template_rules:
  required_fields: [...]
  output_shape: table
  exhaustive: true
source_slices:
  - chapter: 第一百二十三章
    line_start: 6075
    line_end: 6120
    text: "<原文片段>"
candidate_triggers:
  - 丹
  - 丸
  - 药液
output_contract: candidate_card_jsonl
```

分片抽取 agent 输出：

```yaml
status: DONE
cards:
  - item_key: 筑基丹
    item_type: 丹药
    fields:
      丹药名称: 筑基丹
      功效: 辅助炼气修士筑基
      丹方: 原文未说明
    evidence:
      - chapter: 第若干章
        line_start: 6081
        line_end: 6085
        summary: 七派围绕筑基资源组织禁地争夺
    confidence: high
    missing_fields:
      - 具体丹方
    review_flags: []
concerns: []
```

状态含义：

- `DONE`：任务完成，可进入合并或审查。
- `DONE_WITH_CONCERNS`：任务完成但存在疑点，主控 agent 需要把 concerns 传给复核或重抽取流程。
- `NEEDS_CONTEXT`：缺少必要上下文，主控 agent 补充模板、章节、候选或规则后重派。
- `BLOCKED`：无法完成，主控 agent 判断是拆分任务、升级模型、换流程，还是标记为人工复核。

### 动态调度策略

插件不固定“一个模板一个 agent”。调度器根据任务规模动态选择粒度。

1. 小小说、小模板：仍走中间数据抽取闭环，但可把候选召回、分片抽取和字段补全合并为少量 agent 执行。
2. 大小说、实体清单型模板：候选召回 agent 按触发词和章节组并发召回，分片抽取 agent 生成卡片，字段补全 agent 补字段，别名归并 agent 合并同名实体。
3. 大小说、事件链型模板：候选召回 agent 先按章节组抽事件候选，分片抽取 agent 提取阶段事实，链路聚合 agent 再按事件链主题二次聚合。
4. 关系型模板：候选召回 agent 先按人物锚点召回，分片抽取 agent 抽互动事实，链路聚合 agent 按人物关系网合并。
5. 世界空间型模板：候选召回 agent 先按地点、势力、区域关键词召回，分片抽取 agent 按区域分派，字段补全 agent 补空间关系和功能字段。
6. 38 模板全量执行：先共享一次 source/index/candidate 层，再按 route 批量分派模板任务，避免每个模板重复扫全文。

### 中间数据抽取闭环

中间数据阶段必须拆成更细的多 agent 流程，不能只由单个泛化 agent 从原文直接生成 `merged/*.jsonl`。

每个模板或模板批次至少走以下小流程：

1. 候选召回 agent 从轻量索引、模板触发词、章节标题、共现窗口和已发现实体中召回原始候选。
2. 分片抽取 agent 按章节组、候选组或实体锚点并发生成候选卡片。
3. 字段补全 agent 对缺字段候选回查上下文，补齐必填字段；找不到依据时写“原文未说明”或“待核验”。
4. 别名归并 agent 合并同名、别名、重复候选，并保留无法裁决的冲突项。
5. 链路聚合 agent 对事件链、关系链、制度流程、职业流程等跨章节候选进行阶段串联。
6. 证据定位 agent 为每张候选卡片确认章节、行号、短事实摘要和证据状态。
7. 覆盖查漏 agent 按模板写全规则检查章节覆盖、境界覆盖、身份覆盖、地域覆盖、势力覆盖和字段覆盖。
8. 质量审查 agent 对中间数据进行门禁审查；发现漏项时，主控 agent 重派候选召回、分片抽取、字段补全、别名归并、链路聚合或证据定位 agent。

这个闭环的输出才是 writer agent 可读取的 `merged/*.jsonl` 和 audit 报告。

### 38 模板全量生成流程

当用户提供原文和模板目录，并要求生成所有模板文档时，主控 agent 应执行：

1. `scan`：索引 agent 只跑一次，生成编码、分章、行号、倒排索引。
2. `plan-templates`：模板规划 agent 扫描所有模板，修正 route、字段、触发词、输出形态和审计规则。
3. `candidate-pass`：候选召回 agent 按 7 类 route、模板触发词和章节组并发生成共享候选池。
4. `card-extract-pass`：分片抽取 agent 为每个模板按章节组、候选组或实体锚点并发生成候选卡片。
5. `field-complete-pass`：字段补全 agent 为候选卡片补齐模板必填字段或写明缺失原因。
6. `alias-chain-pass`：别名归并 agent 处理实体去重和别名合并，链路聚合 agent 处理事件链、关系链和流程链聚合。
7. `evidence-pass`：证据定位 agent 回查原文，补齐行号和短事实摘要。
8. `coverage-pass`：覆盖查漏 agent 检查章节、境界、身份、地域、势力、场景和字段覆盖。
9. `intermediate-audit-pass`：质量审查 agent 检查中间数据的模板符合性、遗漏风险和过度推断。
10. `intermediate-repair-pass`：对 audit 标红项重派候选召回、分片抽取、字段补全、链路聚合或证据定位 agent。
11. `write-pass`：按待输出模板分派 writer agent，并行写出 Markdown 文档或草稿。例如只写前 5 个模板时，派出 5 个 writer agent 同时读各自的 `merged/*.jsonl`、audit 报告和模板规则，并分别写入 5 个目标文件；全量 38 个模板时按并发上限分批派发。
12. `document-review-pass`：每个 writer agent 写完单篇文档后，分派质量审查 agent 审该 Markdown 是否符合模板、是否完整承接 merged 数据、是否存在遗漏、重复、证据缺失、字段空洞或过度推断。
13. `document-repair-pass`：单篇文档审查未通过时，主控 agent 将审查报告、原 Markdown、模板规则和相关 merged 数据交回 writer agent 修订；修订后再次进入 `document-review-pass`。达到最大返工轮次仍未通过时，标记人工复核，不写成已完成。
14. `final-review`：最终质量审查 agent 汇总跨模板重复、冲突和未解决风险。

这个流程允许大量读取、抽取和写出并发，但每个 writer agent 只能写一个模板文件，且写入前必须获得该文件的独占锁，避免并发覆盖。每个模板文件都有自己的“写出 - 审查 - 返工”小闭环，不因其他模板通过而跳过。

### 单篇文档写出闭环

每个最终分析文档都必须走以下小流程：

1. writer agent 读取该模板的 `merged/*.jsonl`、audit 报告、模板原文和 writer 规则。
2. writer agent 生成或修订单个 Markdown 文档。
3. 质量审查 agent 检查最终 Markdown：
   - 是否严格符合模板章节、字段和输出限制。
   - 是否完整承接 merged 数据，没有漏掉已通过审查的候选。
   - 是否把缺失字段写成“原文未说明”或“待核验”，而不是空白。
   - 是否存在重复卡片、证据缺失、字段空洞、过度推断或混淆原作事实/我的判断。
4. 如果通过，主控 agent 标记该模板文档完成。
5. 如果不通过，主控 agent 将问题清单交给 writer agent 返工，并再次触发质量审查。
6. 如果连续多轮仍无法通过，主控 agent 将该文档标记为人工复核，而不是伪装完成。

### 多 agent 审查门槛

每个模板进入最终写出前必须通过一次综合质量审查：

1. 规格符合性：字段是否完整，格式是否符合模板，是否额外添加模板不要求的章节，是否正确区分原作事实、我的判断、待核验。
2. 质量风险：候选是否可能漏掉，证据是否不足，是否存在只写主角线、只写名场面、只写高阶样本的问题，是否存在无证据推断。

审查未通过时，主控 agent 不直接手工补写，而是根据问题重派对应候选召回、分片抽取、字段补全、别名归并、链路聚合或证据定位 agent。

### 模型选择

- 候选召回、机械分片抽取：使用快速模型。
- 字段补全、别名归并、证据定位：使用标准模型。
- 模板规划、链路聚合、覆盖查漏、最终质量审查：使用最强可用模型。

原则是把最强模型用在判断密度高的地方，把高并发分片任务交给速度更快的模型。

## 质量策略

### 全章覆盖

每章进入哪个模板流程、是否扫描、是否命中候选、是否被子 agent 处理，都必须记录。audit 应明确列出未扫描章节和失败章节。

### 候选池先行

先用关键词、实体模式、章节标题、共现窗口召回候选，再让模型抽取。模型不能凭印象直接生成文档。

### 多轮查漏

每个模板至少三轮：

1. 初扫：按触发词和章节抽候选。
2. 扩展：根据已发现实体、别名、相关事件反查。
3. 审计：按模板字段、境界、地域、身份、势力、场景覆盖维度查缺。

### 证据回填

每条候选必须带原文路径、章节、行号和短事实摘要。找不到证据则降级为“待核验”，不得写成事实。

### 总表与卡片一致性

L3 模板若总表有条目但正文没有对应卡片，audit 必须报错或警告。模板明确不需要卡片时，通过配置关闭该检查。

### 缺失字段显式化

字段缺失不能空白，必须写“原文未说明”或标记“待核验”。这样读者能区分原文缺失、证据不足和插件漏填。

## 速度策略

1. 章节级并发：大文本按章或章组并发处理。
2. 中间数据阶段并发：候选召回、分片抽取、字段补全、证据定位和覆盖查漏可按模板、route、章节组和候选组并发执行。
3. 模板级并发：不同模板可以并发抽取，也可以由多个 writer agent 并行写出；同一模板输出文件必须独占，并且每个输出文件独立完成写出、审查和返工循环。
4. 共享索引：38 模板全量执行时只做一次 source/index。
5. 缓存复用：源文件、模板文件、配置文件未变化时复用索引和候选。
6. 模型调用分层：简单候选用轻量上下文，复杂事件链再使用大上下文和更强模型。
7. 失败局部重试：某章、某模板失败，不影响全局任务。

## 错误处理

| 问题 | 处理方式 |
|---|---|
| 编码识别失败 | 停止该作品，要求显式配置 encoding |
| 分章失败 | 降级为固定字数切片，但 audit 标红 |
| 模板文件缺失 | 阻止该模板执行，报告 README 或配置不一致 |
| 某章模型抽取失败 | 记录失败块，允许后续 resume |
| 子 agent 返回 NEEDS_CONTEXT | 主控 agent 补充上下文后重派 |
| 子 agent 返回 BLOCKED | 拆分任务、升级模型、换流程或标记人工复核 |
| 候选无证据 | 降级为待核验，不得写成事实 |
| 字段缺失 | 写原文未说明或进入 missing_fields |
| 输出文档已有人工修改 | 默认写 `.draft.md`，显式 `--overwrite` 才覆盖 |
| 同名实体冲突 | 保留多条候选，进入人工复核列表 |

## 验证标准

第一阶段至少验证：

1. 编码与分章：使用《凡人修仙传》GBK 大文本，识别编码、转码、得到约 2451 章并保留行号。
2. 模板注册：扫描模板目录和 `templates.yaml`，确认启用模板都有文件、route、字段和输出规则。
3. 候选抽取：对 `丹药分析`、`事件因果链`、`世界观设定` 三种不同范式各跑小范围章节，验证候选结构统一。
4. 多 agent 调度：对一个包含多个章节分片的模板运行候选召回 agent、分片抽取 agent、字段补全 agent、别名归并 agent、证据定位 agent、覆盖查漏 agent 和质量审查 agent，验证状态传递和重试逻辑。
5. 并行写出：选择 5 个模板时分派 5 个 writer agent，同步读取各自中间结果并分别写出 Markdown；确认每个 writer agent 只写自己的目标文件。
6. 文档级质量闭环：人为制造一篇最终 Markdown 漏掉 merged 数据或违反模板字段，确认质量审查 agent 能拒绝通过，并触发 writer agent 返工。
7. 审计：人为制造总表有条目但无卡片、候选无证据、章节未扫描等情况，确认 audit 能报出。
8. 断点续跑：中断一次 run，再 resume，只重跑失败或未完成块。
9. 输出格式：生成 Markdown 严格贴合模板，不额外塞插件说明。

## 第一阶段落地范围

第一阶段做完整闭环，不一次性铺满 38 个模板。

范围：

1. 插件骨架与 CLI。
2. 编码识别、分章、行号索引。
3. 模板注册与路由配置。
4. 多 agent 调度器 MVP。
5. 三个流程型 skill：
   - 实体清单：先覆盖 `丹药分析`、`法宝分析`。
   - 事件链：先覆盖 `事件因果链`、`冲突事件分析`。
   - 世界空间：先覆盖 `世界观设定`、`势力设定`。
6. 中间数据多 agent 抽取闭环 MVP：候选召回、分片抽取、字段补全、别名归并、证据定位、覆盖查漏和质量审查。
7. 中间结果 JSONL。
8. audit 报告。
9. Markdown writer agent 与文档级质量审查返工循环。
10. README 中已删除模板的过期条目清理。

第二阶段补齐关系、制度流程、职业机制、叙事场景等剩余 skill，并扩大到所有模板。

第三阶段在 StoryGraph 稳定后，将 StoryGraph 作为候选来源 adapter 接入，而不是替代主流程。

## 设计模式与配置化自检

通用架构：

- 插件内核不绑定具体小说。
- 作品、模板、流程、字段、触发词、审计规则和输出规则都通过配置声明。
- 子 agent 只处理明确分派的有限任务，主控 agent 负责调度和质量闭环。

设计模式：

- Registry：模板注册表决定模板走哪个流程。
- Strategy：不同 extractor skill 是不同抽取策略。
- Pipeline：索引、候选召回、分片抽取、字段补全、别名归并、链路聚合、证据定位、覆盖查漏、审计、写出逐步执行。
- Adapter：StoryGraph 未来作为候选来源接入。
- Orchestrator：主控 agent 动态分派子 agent 并处理状态。

配置化覆盖范围：

- 作品路径、编码、分章规则。
- 模板文件、输出文件、route。
- 必填字段、触发词、覆盖维度。
- 审计规则、缺失字段写法、证据要求。
- 写出策略、是否覆盖、是否草稿。
- 中间数据多 agent 粒度、writer agent 粒度、并发限制和模型选择策略。

避免硬编码：

- 代码不写具体丹药、法宝、人物、章节或《凡人修仙传》专属规则。
- 项目领域专属范围放在模板和配置中。
- 新增模板优先加配置，只有出现新抽取范式时才新增 skill。

## 用户审核点

请重点审核：

1. 7 类流程型 skill 是否覆盖当前模板目录。
2. 多 agent 调度是否符合你对 38 模板全量生成的预期。
3. 第一阶段只做 6 个模板闭环是否合适。
4. 默认不覆盖已有 Markdown、先写草稿的策略是否符合你的工作方式。
