# 多小说模板抽取可恢复调度设计

> 最后更新：2026-07-02
> 状态：设计已确认
> 类型：世界观参考原文抽取流程规格
> 适用范围：`docs/世界观参考/<作品名>/` 下的小说原文、模板抽取产物和临时调度状态

## 背景

`docs/世界观参考/模板/` 中已有 37 个调研模板，用于把小说原文中的世界观、势力、角色、材料、事件、职业、场景等信息整理成项目可追溯参考文档。单本小说原文较长，若一次性读取全书，会超出上下文并难以恢复；若按模板或章节手动接力，又容易漏状态、重复处理或污染最终文档。

本设计定义一个多小说可恢复抽取调度流程：小说之间可以并发，单本小说内部严格串行；每本小说按章节窗口切分，每个窗口派发一个全新的子 agent；子 agent 在该窗口内按模板顺序逐个维护对应产物文档。

## 目标

- 支持同时处理多本小说，默认全局并发数为 3。
- 单本小说内部保持 `perNovelConcurrency = 1`，避免多个 agent 同时修改同一作品目录下的同名产物文档。
- 每本小说按 `5` 章一个窗口切分，并保留 `1` 章重叠：`1-5`、`5-9`、`9-13`，直到全书结束。
- 每个窗口由一个新子 agent 处理；该 agent 必须按模板顺序处理全部模板。
- 状态精确记录到 `novel_id + chunk_id + template_name`，支持中断后从未完成模板继续。
- 输出文档生成在小说原文所在目录，不生成到临时目录。
- 临时目录只保存分块、状态、日志、锁和 agent 交接材料。

## 非目标

- 不在本规格中实现具体调度器代码。
- 不改变模板文件本身的字段要求。
- 不把世界观参考文档直接确认为项目 Wiki；进入 `docs/worldbuilding/wiki/` 前仍需用户确认。
- 不使用哈希、指纹或 golden 一致性作为质量证明。

## 总体架构

```text
总调度器
├── 小说 worker：斗破苍穹
│   ├── chunk-0001：第001-005章 -> 新子 agent -> 37 个模板顺序处理
│   ├── chunk-0002：第005-009章 -> 新子 agent -> 37 个模板顺序处理
│   └── ...
├── 小说 worker：凡人修仙传
│   ├── chunk-0001：第001-005章 -> 新子 agent -> 37 个模板顺序处理
│   └── ...
└── 小说 worker：仙逆
    ├── chunk-0001：第001-005章 -> 新子 agent -> 37 个模板顺序处理
    └── ...
```

总调度器负责全局队列、并发控制、状态恢复和子 agent 派发。小说 worker 是逻辑上的单本小说执行流，不要求常驻进程；它的职责是保证同一作品目录内同一时间只有一个窗口 agent 在写文档。

子 agent 只处理一个窗口，不能跨窗口继续处理，也不能处理其他小说。窗口完成后，主调度器创建新的子 agent 处理下一窗口。

## 目录约定

以《斗破苍穹》为例：

```text
docs/世界观参考/斗破苍穹/
├── 斗破苍穹.txt
├── 材料分析.md
├── 丹药分析.md
├── ...
└── .novel_extractor/
    ├── config.json
    ├── state.sqlite
    ├── chunks/
    │   ├── chunk-0001.md
    │   ├── chunk-0002.md
    │   └── ...
    ├── task-packets/
    │   └── chunk-0001.md
    ├── logs/
    │   └── novel-extractor-YYYYMMDD-HHMMSS.jsonl
    └── locks/
        └── novel.lock
```

`.novel_extractor/` 为临时和可恢复状态目录。最终调研文档全部位于作品目录根部，例如 `材料分析.md`，文件名由模板名去掉 `模板` 得到。

## 配置模型

调度配置使用 JSON 或等价结构保存，不把小说路径、模板列表、窗口大小、并发数写死在代码中。

```json
{
  "globalConcurrency": 3,
  "perNovelConcurrency": 1,
  "windowSizeChapters": 5,
  "overlapChapters": 1,
  "templateMode": "sequential",
  "resumeMode": "chunk_and_template",
  "templateDir": "docs/世界观参考/模板",
  "novels": [
    {
      "id": "dou_po_cang_qiong",
      "name": "斗破苍穹",
      "sourceText": "docs/世界观参考/斗破苍穹/斗破苍穹.txt",
      "outputDir": "docs/世界观参考/斗破苍穹"
    }
  ]
}
```

模板顺序以模板目录的稳定清单为准，优先读取 `docs/世界观参考/模板/README.md` 的模板清单；若实现脚本需要机器可读顺序，可以从 README 生成或维护独立配置文件。

## 分块规则

分块器读取小说原文，识别章节标题，例如 `第001章 陨落的天才`。每个窗口包含 5 章，并与上一个窗口重叠 1 章。

示例：

| chunk_id | 章节范围 | 说明 |
|----------|----------|------|
| chunk-0001 | 第001-005章 | 首窗口 |
| chunk-0002 | 第005-009章 | 与上一窗口重叠第005章 |
| chunk-0003 | 第009-013章 | 与上一窗口重叠第009章 |

重叠章节用于让跨章信息有上下文。子 agent 处理重叠章节时必须去重：如果上一窗口已经写入同一事实，本窗口只能补充证据、修订表述或移动待定项，不能重复新增同一条目。

## 子 Agent 执行契约

每个子 agent 的输入包括：

- 当前小说名、原文路径、输出目录。
- 当前 `chunk_id`、章节范围、分块文本路径。
- 模板目录和模板顺序。
- 当前窗口之前已存在的 37 个产物文档。
- 抽取规则、待定区规则、禁止事项和完成条件。

子 agent 必须按以下循环执行：

1. 读取当前窗口文本。
2. 按顺序读取一个模板，例如 `材料分析模板.md`。
3. 打开对应产物文档，例如 `材料分析.md`；若不存在，则按模板推荐结构创建。
4. 对产物文档执行增删改查。
5. 更新该模板处理状态和窗口日志。
6. 进入下一个模板。

增删改查规则：

- 新事实有足够证据时，写入模板要求的正文、表格或案例区。
- 信息较少但可能有价值时，写入文末标准“待定区”。
- 后续窗口出现更完整证据时，将待定项移动到正文或案例区，并保留必要证据说明。
- 发现重复条目时合并，不重复写卡片或表格行。
- 发现旧内容证据不足时，标注“待核验”或移动到待定区。
- 不编造原文没有的设定，不把训练印象或其他作品内容混入当前作品。
- 不粘贴大段原文，只写章节、路径、行号或短事实摘要作为证据。

## 待定区规则

每个产物文档可以在文末保留一个标准区块：

```md
## 待定区

| 条目 | 当前线索 | 缺失信息 | 来源窗口 | 后续处理 |
|------|----------|----------|----------|----------|
```

待定区用于保存“当前信息很少，但可能后续变重要”的线索。待定项有三种状态：

- `待补证`：目前只出现短线索，等待后续章节。
- `已升级`：后续证据充分，已经移动到正文或案例区。
- `不采信`：后续长期没有出现，或确认价值不足、疑似误判。

当待定项升级或不采信时，子 agent 应在日志中记录来源窗口、处理原因和目标位置，避免后续 agent 反复处理同一线索。

## 状态与恢复

状态库至少记录以下实体：

| 实体 | 关键字段 |
|------|----------|
| novel_run | novel_id、source_text、output_dir、status、started_at、updated_at |
| chunk | chunk_id、chapter_start、chapter_end、text_path、status |
| template_task | novel_id、chunk_id、template_name、output_doc、status、started_at、finished_at、error |
| pending_item | novel_id、doc_name、item_key、status、source_chunk、last_seen_chunk |
| event_log | timestamp、novel_id、chunk_id、template_name、event_type、message |

恢复逻辑：

1. 总调度器启动后读取每本小说的 `state.sqlite`。
2. 若存在 `running` 但没有有效锁的任务，将其标记为 `interrupted`。
3. 从第一个 `pending`、`failed` 或 `interrupted` 的 `template_task` 继续。
4. 若某个窗口中途失败，只恢复该窗口未完成模板，不重跑已经标记完成的模板。
5. 只有当前窗口 37 个模板都完成后，才允许该小说进入下一窗口。

锁粒度为单本小说目录。全局允许 3 本小说并发，但同一本小说不能同时有两个窗口 agent 写文档。

## 日志与审计

每个窗口完成后写入窗口摘要，至少包含：

- 本窗口章节范围。
- 处理过的模板数量。
- 新建、更新、合并、删除或移动的条目摘要。
- 新增待定项数量、升级待定项数量、不采信待定项数量。
- 无新增信息的模板列表。
- 失败模板和错误信息。

日志使用 JSONL，便于后续统计和恢复。最终交付报告应区分真实已处理窗口、已完成模板任务和仅由日志记录的待核验事项。

## 验证标准

流程级验证：

- 分块清单覆盖全书章节，没有章节缺失。
- 相邻窗口只有预期的 1 章重叠。
- 每本小说同一时间只有一个有效锁。
- 状态库能定位到当前小说、当前窗口、当前模板。
- 人为中断后能从未完成模板恢复。

内容级验证：

- 每个产物文档保留模板要求的元信息和结构。
- 输出文档的资料来源能追溯到当前作品原文。
- 待定区条目有来源窗口和后续处理状态。
- 重叠章节没有造成重复卡片或重复表格行。
- 文档中没有把待核验内容写成原作事实。

## 风险与处理

| 风险 | 处理 |
|------|------|
| 多 agent 同时写同一作品文档 | 单小说锁 + `perNovelConcurrency = 1` |
| 重叠章节导致重复抽取 | 子 agent 必须先读现有产物文档并执行合并规则 |
| 长任务中断 | 状态精确到 `chunk_id + template_name` |
| 模板数量或名称变化 | 模板清单配置化，不在代码中写死 37 |
| 待定区无限膨胀 | 每次窗口处理时维护 `待补证 / 已升级 / 不采信` 状态 |
| 内容质量漂移 | 窗口日志 + 关键文档人工抽查 + 模板结构校验 |

## 确认结论

采用“小说之间并发、小说内部串行”的可恢复调度方案。默认全局并发处理 3 本小说；每本小说按 5 章窗口、1 章重叠切分；每个窗口派发一个全新子 agent；子 agent 在窗口内按模板顺序维护 37 个产物文档；状态和日志保存在作品目录下的 `.novel_extractor/`，最终文档生成在作品目录根部。
