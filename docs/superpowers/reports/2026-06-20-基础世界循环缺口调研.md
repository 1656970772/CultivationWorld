# 基础世界循环缺口调研报告

> 最后更新：2026-06-20

## 任务目标

回答当前项目在“基础世界循环”层面还缺什么，以及用户现在最应该优先做什么。本报告只整合多 Agent 调研结论与当前项目证据，作为需求补充和缺口报告；不包含代码实现方案，不新增运行时 JSON 数据。

## 调研范围

- 世界 Tick 与 `WorldEngine` 装配。
- NPC 行为、Job/Toil、任务、物品、经济、关系、妖兽、动态事件、死亡与继承。
- 运行时数据配置和验证/观测工具。
- 世界观规则中影响基础循环完整度的中间层规则。

## 证据来源

- 架构 Agent 结论：`WorldEngine` 初始化和 Tick 顺序已经形成基础循环；架构侧无阻塞 P0。
- 数据 Agent 结论：74 物品、10 任务、59 个可加载 action/world-rule template、25 job、45 toil、关系平台、经济场景和 GAS 资产已经存在；数据侧无阻塞 P0。
- 世界观 Agent 结论：当前最缺的是承接世界循环的中间层规则，不是更大规模世界观堆料。
- 验证 Agent 结论：`test-game-data-validation` 通过；`profile-npc-execution` 能采集 3 天、126 NPC、378 records，其中 66 条非 idle；性能与闭环摘要工具仍有缺口。
- 当前项目文件证据：`apps/game/js/engine/world-engine.js`、`apps/game/js/engine/world/tick-manager.js`、`apps/game/data/`、`apps/game/tools/`、`docs/` 下现有系统文档与验证报告。
- 数量口径以当前配置文件/manifest 加载范围为准；本报告保留 Agent 调研结论，但关键数量使用可复核文件统计。

## 结论摘要

基础世界循环已经存在，可以继续在真实模拟中迭代；当前不需要先推倒重做引擎。架构/数据两个调研口径均认为没有阻塞基础循环的 P0。下一轮最有价值的工作，是把“事件为什么发生、任务为什么失败、市场为什么缺货、地域为什么危险、道具为什么有价”这些中间规则补齐，并通过配置和少量通用结算模块让它们进入真实 Tick。

换句话说，现在的问题不是“世界不会动”，而是“世界已经会动，但因果、供需、失败后果和地域生态还不够解释得通”。

## 我目前该干什么？

1. **先统一规则文档口径**：优先补 `docs/worldbuilding/wiki/` 和 `docs/systems/` 中的道具经济总则、任务委托生态总规则、地域危险与资源分布、动态事件因果与仲裁规则，避免后续配置和代码各写各的。
2. **再补配置层的基础缺口**：围绕生产配方、市场供给/库存、任务模板结构化目标/失败/关系后果、动态事件模板，把规则沉淀到 `apps/game/data/` 的正式配置，而不是写进一次性脚本。
3. **随后补少量通用结算能力**：动态事件结算因果、冲突仲裁、任务失败后果、经济/任务关系事件应走通用服务或策略注册，不要为某个事件或任务硬编码。
4. **补观测工具闭环**：让 `simulate-analysis.mjs` 输出机器可读摘要，让 profiler 汇总出“谁在做什么、为什么空闲、循环卡在哪里”，再用真实模拟指标决定下一轮平衡。
5. **暂缓大表现和高阶内容**：高阶天劫、完整妖兽社会、凡人王朝、逐境界特色玩法可以排进 P2，不要抢在基础因果和供需闭环之前。

## 推荐下一轮实施顺序

1. **文档/规则统一**：先写道具经济总则、任务委托生态总规则、地域危险与资源分布、动态事件因果/仲裁规则，并同步 `docs/README.md` 导航。
2. **配置层补齐**：补生产配方、市场库存/供给、任务结构化目标/失败/关系后果、动态事件模板，确保字段和命名进入 `docs/data/data-config-rules.md`。
3. **少量代码结算能力**：只补通用读取和结算，不写专用事件逻辑；优先扩展现有 registry、service、Job/Toil、关系平台和经济平台。
4. **观测能力闭环**：修 `perf-profile` 配置加载；给 `simulate-analysis` 增加摘要输出；给 profiler 增加聚合视图。
5. **真实模拟复核**：用多种子、足够天数、全量 NPC 的真实模拟观察 P1 是否改善，而不是只看单点样例。

## 暂不建议做

- 大而全世界观设定集：现在更需要能落到 Tick 的中间规则，而不是先扩写所有宗教、神话、远古历史。
- 全 3D 或表现升级：基础因果、供需、任务失败和观测工具未闭环前，表现升级收益较低。
- 完整高阶天劫：可以保留为后续境界特色，但不应早于基础任务、经济、地域危险和事件结算。
- 完整妖兽社会：先补族群/巢穴/领地/兽潮的最小生态，再考虑复杂妖族政体。
- 大规模新增物品或任务数量：先补规则、模板和消耗面，再扩数量，否则会放大配置债。

## 验收标准

下一轮补齐 P1 后，建议按以下标准验收：

| 验收维度 | 建议验证 | 真实行为指标 |
|----------|----------|--------------|
| 数据合法性 | `node apps/game/tools/test-game-data-validation.mjs` | 新增配置全部通过 strict validation；无未登记引用。 |
| 任务/经济/关系闭环 | 运行任务、经济、关系相关测试，并补覆盖任务失败/关系后果的测试。 | 任务完成、失败、拖欠、奖励、关系变化和经济账本能在同一模拟中出现。 |
| 动态事件结算 | 运行动态事件 action/job/system 测试和真实模拟。 | 事件有参与者、贡献、结算、奖励/损失、关系或信息后果。 |
| 市场与配方 | 对配方、库存刷新、交易和消耗做平台测试。 | 库存会变化，供需影响交易，生产会消耗输入并产出结果。 |
| 长程真实模拟 | 使用 `simulate-analysis.mjs` 或后续摘要模式跑多种子长程模拟。 | 非 idle 比例、任务完成/失败、市场库存变化、关系事件、妖兽死亡/补充、动态事件结算数量可观察。 |
| NPC 执行观测 | 使用 `profile-npc-execution.mjs` 和后续聚合视图。 | 能看到主要行为分布、replan 原因、Job/Toil 卡点，且能解释下一轮调参方向。 |
| 性能观测 | 修复后运行 `perf-profile.mjs`。 | 性能脚本使用正式 manifest 配置，输出能对应真实世界初始化和 Tick。 |

## 最终判断

当前项目已经具备“世界自己运转”的基础：Tick 在推进，NPC 会行动，任务/物品/经济/关系/妖兽/动态事件/死亡继承都已接入不同程度的真实循环。下一阶段不要从零重写，也不要急着扩大全量内容；应优先把 P1 的因果、供需、失败后果和规则配置补齐，让世界从“能动”变成“动得有理由、有代价、有后续”。
