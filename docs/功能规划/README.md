# 功能规划文档

> 最后更新：2026-06-19  
> 用途：持续记录、整理和拆分本项目计划要做的所有功能。

## 目录定位

本目录用于沉淀项目未来功能规划。用户可以持续输入功能点、想法、规则、玩法、系统需求或实现取舍，Codex 负责把内容总结到合适的位置，并保持文档结构清晰、可追踪、便于后续拆分。

当前先维护一份总文档：

- `总功能清单.md`：集中记录所有待规划、待拆分或已确认的功能点。

## 持续整理规则

1. 用户后续每输入一个或多个功能点，Codex 都应总结后写入本目录下合适的文档位置。
2. 只有当用户明确说出“功能规划”时，才把后续输入的功能内容写入本目录；如果用户只是提问、讨论或提出其他任务，但没有说“功能规划”，不要写入本目录。
3. 写入前应先对照本目录已有文档；如果用户新说的内容与之前文档中已记录的内容存在冲突、覆盖或明显口径不一致，Codex 应主动反馈冲突点，让用户确认后再整理落文。
4. 写入时应整理标题层级、条目归类、表述风格和重复内容，避免把原始对话堆成流水账。
5. 如果用户一次输入内容较多，或同一主题已经变得复杂，Codex 应主动提出拆分建议。
6. 是否拆分为多个目录、多个文档，由用户视情况决定；未得到确认前，默认继续维护当前总文档。
7. 后续拆分时，应保留清晰导航，并在本 README 中更新目录说明。
8. 功能点若涉及已确认的设计决策、世界观设定、数据规则或架构决策，应同步记录到项目对应文档中，而不是只留在本目录。
9. 功能规划不直接等同于实施计划；进入编码前仍需按项目规则检查通用架构、设计模式适配和配置化覆盖范围。

## 建议拆分信号

当出现以下情况时，Codex 应提醒用户考虑拆分文档：

- 单个系统的功能点超过 8-10 条，且开始包含规则、状态、数据结构或流程。
- 多个功能点已经形成独立子系统，例如修炼、战斗、门派、经济、任务、UI、编辑器等。
- 同一功能需要记录目标、玩家体验、数据配置、运行规则、验证方式等多类信息。
- 总文档阅读成本明显升高，或某一类内容频繁被追加、修改、重排。

## 维护格式

- 默认使用简体中文。
- 每个文档头部保留“最后更新”字段。
- 功能条目优先写成“目标 / 功能点 / 备注或待确认”的结构。
- 未确认内容标记为“待确认”，不要写成已经确定的实现方案。
- 已拆分内容在总文档中保留摘要和链接，不重复维护大段正文。
